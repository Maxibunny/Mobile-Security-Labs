**Реализовано в исходниках:**

1. Создание аккаунта и вход по Email/Password посредством Firebase Authentication (без анонимных пользователей).
2. После успешной регистрации: `CredentialManager.createCredential(CreatePasswordRequest)` — предложение сохранить пароль в системном менеджере.
3. На входе: **один** `GetCredentialRequest` с `GetPasswordOption` и `GetGoogleIdOption`; Google ID token проверяется Firebase `signInWithCredential`.
4. Профиль показывает UID, email, имя, последний способ входа, привязанные провайдеры.
5. TODO и профиль находятся в отдельном навигационном графе, доступном только при Firebase Auth; Firestore Rules ограничивают запросы по UID на сервере.
6. Выход из Firebase, очистка состояния Credential Manager, пересоздание навигационного стека; Back не возвращает в TODO.

## Важные ограничения

- На экране регистрации пароль временно содержится **только в оперативной памяти** полей ввода и передаётся в Firebase и Credential Manager. Приложение не записывает пароль в SharedPreferences, базу данных и собственные файлы. Firebase Auth самостоятельно управляет своими сессионными данными.
- Firebase сохраняет аутентифицированную сессию после перезапуска. Это ожидаемое поведение: пользователь остаётся авторизованным до выхода; при отсутствии сессии защищённый граф не создаётся.
- Системное предложение сохранить пароль может не появиться без настроенного менеджера паролей, актуальных Google Play Services, подходящей учётной записи и разрешений/настроек пользователя.
- Если Google и email относятся к одному адресу, Firebase может требовать связать провайдеры при конфликте существующего аккаунта. Автоматическое связывание без повторной верификации намеренно не выполнено.
- При выходе система не удаляет сохранённые пароли — это управляется пользователем в менеджере паролей.
- Встроенная кнопка удаления аккаунта из исходного примера убрана из профиля; удаление с очисткой серверных записей не входит в условия лабораторной и требует отдельной реализации.
