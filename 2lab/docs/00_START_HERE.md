# Начните отсюда: ЛР №2 «Разрешения, компоненты и IPC»

Это **учебная карта реального кода в папке `2lab`**, подготовленная для самостоятельного чтения и защиты. Внутри два отдельных Android-приложения: `notes` (владелец базы) и `client` (читает лишь заголовки). Цель работы — не просто запустить заметки, а контролировать, кто может входить в компоненты Android и какие данные получает.

## Короткая модель работы

```text
Пользователь
    │
    ▼
notes/MainActivity → NotesNavHost → NotesListScreen / NoteScreen
                              │                        │
                              ▼                        ▼
                     NotesListViewModel          NoteViewModel
                              └───────────┬────────────┘
                                          ▼
                                    NotesRepository
                                          ▼
                                        NoteDao
                                          ▼
                                      Room notes.db

Из внешнего мира есть специальные входы:
  notes://note/<id> → MainActivity → NoteDeepLink → проверка id в Room
  уведомление       → immutable PendingIntent → MainActivity / private Receiver
  «Поделиться»       → FileProvider → только cacheDir/exports/
  client             → ContentResolver → TitlesProvider → только id/title
```

**Ключевая мысль для защиты:** Android сам ограничивает доступ на границе компонентов (`exported`, `signature`, `URI grant`), а приложение дополнительно проверяет недоверенные данные. Одни проверки не заменяют другие.

## Где посмотреть код

Корень проекта (`settings.gradle.kts`) содержит два модуля. Исходники Notes находятся в `notes/src/main/java/edu/androidsec/notes/`, клиента — в `client/src/main/java/edu/androidsec/notes/client/`. Системные правила — в двух `src/main/AndroidManifest.xml`. Тесты — в `notes/src/androidTest/`. Автозапуск — `START_LAB2.cmd` / `CHECK_LAB2.cmd` / `scripts/auto_run_windows.ps1`. **Критерии преподавателя** — неизменённый `scripts/check.sh`.

## Как показать приложение без ручного ADB

Распакуйте архив, откройте папку `2lab`, дважды нажмите `START_LAB2.cmd`. Сценарий попробует построить оба APK, поднять уже созданный AVD, установить их без streaming, проверить `check.sh all` и выполнить AndroidTest. Для повторного запуска уже собранного APK используйте `CHECK_LAB2.cmd`. Результат — в `logs/auto-ДАТА-ВРЕМЯ/summary.txt`; фактический вывод проверки сохраняется в `docs/evidence/check-all.txt`.

**Не обещание:** автоматизация не создаёт новый AVD, не принимает SDK-лицензии и не может подтвердить вручную поведение пользовательских экранов или чужого сертификата. Для последних есть отдельные инструкции.

## Какие результаты уже известны

В предоставленном журнале пользователя (21.10.2026, Android 16 API 36, Pixel_8) зафиксировано `scripts/check.sh all: PASS=18 FAIL=0`, обе APK установились (`Success`), сборка успешна, инструментальная AndroidTest-сборка успешна и тесты проходили на том же эмуляторе. **Это результаты прежней версии исходников, полученные на компьютере пользователя**, а не тест после добавления учебных комментариев. Здесь нет возможности проверить эмулятор из этого архива на Windows — запустите снова после распаковки.

Непроверенные полностью вещи: положительный случай `client` с той же подписью (нужно увидеть заголовки), отрицательный случай с другим ключом (нужно увидеть отказ), UX разрешения на уведомления после двух отказов, корректный реальный экспорт в другое приложение, бонус HTTPS App Links. `PASS=18` **не заменяет** эти проверки.

## Что важно не изменять

Имена пакетов, authority, permission, receiver/action, deep-link scheme/host и канал уведомлений зафиксированы заданием. В комментариях объясняется их смысл, но значения оставлены неизменными. Отдельный список — в [SECURITY_WALKTHROUGH.md](SECURITY_WALKTHROUGH.md).
